# Пояснение по SOLID

## S - Single Responsibility Principle
В исходном коде единственный метод processOrder (~80 строк) совмещал пять разных обязанностей: валидацию, расчёт 
скидки, расчёт комиссии, формирование чека и «сохранение» заказа. Любое изменение в одной из них требовало лезть в 
общий метод и рисковало сломать остальные. 
Исправление: валидация вынесена в OrderValidator, печать чека - в ReceiptPrinter, расчёт скидки - в DiscountStrategy, 
расчёт комиссии - в CommissionStrategy, а OrderService теперь только координирует эти компоненты. У каждого класса одна 
причина для изменения.

## O - Open/Closed Principle
В исходном коде добавление нового типа клиента или способа оплаты требовало дописать ещё один else if в тот же 
80-строчный метод - то есть изменить уже работающий и протестированный код, рискуя задеть соседнюю логику. 

Исправление: новый тип добавляется без правки OrderService - достаточно новой константы в CustomerType/PaymentType, 
нового класса-стратегии и одной строки в Map внутри соответствующей фабрики. Класс OrderService закрыт для изменения, но 
открыт для расширения.

## L - Liskov Substitution Principle
В исходном коде иерархии расчётных классов не было вовсе - вся логика лежала в if/else внутри processOrder, поэтому 
говорить о подстановке реализаций не приходилось: любое изменение расчёта означало правку общего метода. 

Исправление:  введены интерфейсы DiscountStrategy и CommissionStrategy с реализациями (RegularDiscount, VipDiscount, 
PremiumDiscount, CardCommission, CashCommission, TransferCommission), и все они соблюдают единый контракт 
calculate(Order): double - возвращают неотрицательную величину, не бросают исключений на валидном заказе и не зависят 
от конкретного класса-клиента. OrderService работает через интерфейс, поэтому любую реализацию можно подставить вместо 
другой без изменения клиентского кода и без нарушения ожидаемого поведения.

## I - Interface Segregation Principle
В исходном коде «интерфейсом» фактически был сам класс OrderService с единственным публичным методом, который тянул
за собой все внутренние обязанности - клиент, которому нужен только расчёт скидки, всё равно зависел от всего метода
целиком. 

Исправление: интерфейсы сделаны узкими и специализированными - DiscountStrategy и CommissionStrategy содержат ровно по
одному методу calculate. Никто не обязан реализовывать лишние методы, а OrderService зависит только от тех операций, 
которые реально использует.

## D - Dependency Inversion Principle
В исходном коде OrderService напрямую зависел от конкретных процентов и ключей ("VIP", "CARD"), зашитых в
тело метода - модуль высокого уровня зависел от деталей низкого уровня. 

Исправление: OrderService зависит только от абстракций - интерфейсов DiscountStrategy и CommissionStrategy - и от 
фабрик, которые возвращают эти интерфейсы. Ни одного конкретного класса стратегии OrderService не импортирует.

# Применённые паттерны

## Strategy
DiscountStrategy и CommissionStrategy с реализациями под каждый тип клиента и способ оплаты. Позволяет менять 
алгоритм расчёта независимо от OrderService.

## Factory Method 
DiscountStrategyFactory.create(String) и CommissionStrategyFactory.create(String) инкапсулируют выбор конкретной 
стратегии по строковому ключу. Внутри используется Map<Enum, Supplier<Strategy>> с ключом-enum 
(CustomerType, PaymentType), что убирает switch/if-else и делает добавление нового типа расширением, а не правкой.
